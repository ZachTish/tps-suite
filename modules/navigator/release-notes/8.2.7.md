# TPS Notebook Navigator 8.2.7

Navigator could show **Unable to create daily note** during startup even when today's note existed. It opened the Daily Note homepage before enabled GCM had finished publishing its note API, interpreted unavailable identity as a missing note, then entered creation's safety guard. The template was not invoked in that reproduced failure.

The homepage now retains its existing pending request and completes it once through the already registered GCM API-ready event. Repeated announcements do not reopen the note or repeat creation. An explicit command consumes an older pending request, and a controller unloaded while creation is awaiting a result cannot subsequently open or reveal that result. Already-entered creation drains normally.

This is a backward-compatible **patch**, with minimum Obsidian **1.11.0** unchanged. Tested in **Obsidian Plugin Test Vault** on macOS/Obsidian **1.14.4**, ready for the user's BRAT pull. No production installation is claimed.

## Contracts

- No new timer, polling, listener, cache, state store, fallback creator, repair, setting, default or migration.
- Generic Daily Note creation remains fail-closed, and GCM remains the existing creation owner when enabled.
- Absent/disabled GCM and other homepage types keep their existing routes.
- Property-catalog import and homepage continuation have independent error handling.
- The existing Daily Note template, Templater user script and user identifiers are unchanged.

## Validation

- **82/82 focused checks**, including 23 new regressions using the actual controller and the extracted existing main event callback. Source tests cover existing/missing notes, creation disabled, 100 blocked/ready events, command precedence, pre-layout events, first-launch activation, settings changes, shutdown during deferred creation, and independent catalog failures. Host/provider/presentation boundaries are mocked in source tests.
- The unchanged source reproduces the exact startup error without template invocation. Blocked bursts now perform zero source lookups, body reads, inventories, mutation attempts or notices. Existing notes open once without ensure; missing notes delegate one ensure and open the final returned file.
- Full versioned suite: **3,368/3,368 in 287 files**, Node **24.19.0**. Full ESLint: zero errors, the same 26 existing warnings. Style lint, namespace, artifact/operational identity, scoped formatting, TypeScript, string/locale and separate ordinary build pass.
- Stable TEST deployment and targeted reload verify **8.2.7** alongside GCM **8.1.1** and all eight active TPS consumers.
- Installed foreground controlled-readiness QA: 20 blocked announcements produce **0 raw reads, 0 cached reads, 0 inventories, 0 mutation attempts** and no Daily Note warning. 20 ready events produce **1 lookup, 1 open, 0 ensure calls**, preserving the synthetic body. The installed 8.2.6 baseline warns and never resumes. The first candidate harness overlapped manual startup initialization with the real plugin layout callback; its final pass begins after that callback settles.
- One actual foreground full renderer warm reload enables both Core Daily Notes startup and Navigator Daily Note homepage, with a pre-existing synthetic target and an empty template. Real GCM discovery finishes and the correct Daily Note is active, with unchanged body and no pending request.
- Temporary defaults/instrumentation are restored; two owned fixtures are archived byte-identically. Recorded Core, community-plugin, GCM and Navigator settings are byte-identical to baseline. No outbound automation or production notes were changed by QA.

## Limits

Production was inspected narrowly to establish installed versions and Daily Note configuration. Production timing and a captured production cold-start trace are not supplied. A full quit/reopen, physical iPhone and minimum-version acceptance remain pending. The real warm-reload check used an existing note and an empty template; missing-note delegation is covered by source tests, and the configured script's creators were verified separately in the earlier template task. No overall startup-speed claim follows from these correctness checks.
